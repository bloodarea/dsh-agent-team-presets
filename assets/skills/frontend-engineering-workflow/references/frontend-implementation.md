# 前端实施与改进

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、前端实施：直接完成代码

1. 确认任务范围、验收条件、涉及路由与组件，以及文件修改权归属。
2. 编辑前阅读项目工程说明，并检查相关现有实现。
3. 优先复用项目现有框架、组件库、状态管理约定、设计令牌、资源和测试模式。没有明确收益和授权，不引入新依赖、不替换既有技术方案。
4. 以满足需求的最小实现为目标。只有在确实减少重复或复杂度时才抽取复用组件，不为假设中的未来需求提前抽象。
5. 完整处理当前功能涉及的用户可见状态，包括适用的加载、空数据、错误、校验、禁用、选中、成功和响应式状态。
6. 涉及跨层契约时，确认请求与响应字段、业务状态、错误语义和加载行为；不根据偶然的实现细节猜测后端语义。
7. 添加或更新有针对性的前端测试。测试有意义的用户行为，不要只测试实现细节。
8. 根据变更运行必要检查：专项测试、类型检查、Lint、构建，以及适用的真实页面验证。
9. 任务要求截图或响应式视觉验证时，读取并遵循 `references/visual-qa.md`；不得把它当作独立 Skill 调用，也不要用源码检查代替渲染证据。

## 二、前端改进：优化已有实现

适用于响应式布局、组件复用、交互细节或设计系统迁移等有明确边界的改进。

- 明确改进维度、文件和路由范围。
- 保留无关布局、视觉身份、行为和 API 契约。
- 窄范围改进请求不代表可以顺便全面重设计或进行无关重构。
- 视觉或交互改进应尽可能提供前后对比证据；无法取得修改前证据时，不得伪造前后对比，应记录证据限制。

## 三、协作与权限

- 使用团队现有的 `agent-leader-communication` 约定进行咨询和交接，不另建通信协议。
- API、数据语义、权限或跨层设计不明确时，咨询后端架构师。
- 队长将常规实施任务分配给 Executor 时，按约定交接，不得抢占已经分配的工作。
- 未获授权不得修改后端所属文件、共享配置或共享测试基础设施。
- 未获单独授权不得提交、推送、发布、部署或改写 Git 历史。

## 四、完成报告

只报告有实际价值的信息：

- 修改范围及涉及的路由、组件；
- 做出的视觉和交互决策；
- 修改文件；
- API 与数据假设，以及已进行的技术咨询；
- 实际运行的测试和页面检查；
- 截图或证据位置；
- 尚存偏差、阻塞和未验证事项。

代码能够编译，不代表任务已经完成。
