# 前端视觉质量验收

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、目的

检查用户实际看到和操作的界面，发现视觉、响应式布局和可见交互状态中的缺陷，并在获派前端范围内修复。

本工作流以真实渲染证据为依据。它不替代设计方向制定、通用代码审查、后端测试或产品需求评审。

## 二、适用场景

以下情况使用本工作流：

- 前端实现完成后需要视觉验收；
- 用户要求检查页面视觉缺陷；
- 需要对照已批准截图、设计约定或现有产品基线；
- 检查响应式布局、裁切、溢出、遮挡、可见交互状态或视觉回归；
- 前端专项修复需要提供修改前后的渲染证据。

以下情况不应使用：

- 纯后端变更；
- 仅修改文档或 Skill；
- 通过源码即可确认的静态令牌查询；
- 决定新的视觉方向；
- 与渲染表现无关的通用代码质量、安全或架构审查。

## 三、证据与工具约定

1. 阅读项目说明、任务验收条件、现有设计系统、目标路由、变更文件和已批准的视觉参考。
2. 如果项目已经配置 UI Testing 集成或适配器，优先使用它进行浏览器交互、截图、元素检查、请求证据和视觉比较。
3. 优先复用团队已有 UI Testing 工具链，不要把某一种 Browser MCP 或 Playwright MCP 写成强制依赖。
4. 只能使用当前会话实际可调用的工具。不能根据项目安装了某个依赖、服务器正在运行或过去会话使用过某工具，就推断当前工具可用。
5. 如果无法进行真实浏览器截图，应明确说明哪些检查受阻，只完成现有证据能够支持的检查。不得用源码检查冒充视觉验证。
6. 保留证据上下文：路由、视口、应用状态、测试数据条件，以及截图路径或工具证据引用。

## 四、工作流程

### 1. 确定检查范围

明确：

- 目标路由、页面、组件和变更文件；
- 需要检查的桌面、平板、手机或嵌入式视口；
- 必须覆盖的状态：加载、空数据、错误、校验、禁用、选中、悬停、焦点和成功等；
- 已批准的设计方向或当前产品基线；
- 当前任务是只报告问题，还是授权直接修复。

默认检查变更涉及的范围或明确指定的范围。没有要求时，不要扫描整个前端项目。

### 2. 建立基线

- 修改前先捕获当前真实渲染状态。
- 存在已批准的视觉参考时，以它为对照。
- 没有截图参考时，使用现有产品设计系统和相邻页面作为基线。
- 如果基线本身含糊或互相矛盾，应报告需要 UI 工程师或队长决定的设计问题。不要把视觉审计变成未经授权的重新设计。

### 3. 检查真实渲染与交互

根据任务选择相关检查项：

- **层级：** 主操作、页面标题、内容分组、视觉强调和阅读顺序；
- **几何：** 对齐、间距、尺寸、信息密度、节奏和一致性；
- **渲染：** 溢出、裁切、换行、截断、重叠、遮挡和滚动行为；
- **响应式：** 支持的宽度、方向、缩放和容器约束；
- **表面表现：** 字体、颜色角色、对比度、边框、阴影、图标和资源加载；
- **交互状态：** 悬停、焦点、按下、选中、禁用、加载、空数据、错误、校验和成功；
- **固定定位元素：** 内容是否被页头、页脚、抽屉或操作栏遮挡；
- **影响可见结果的运行信号：** 控制台错误、请求失败、资源缺失和数据渲染异常。

使用真实且符合契约的边界数据，例如较长但合理的名称、空集合、单项集合、大数量、缺失的可选值和边界数值。不要用没有实际意义的字符洪水代替真实数据。

### 4. 分类记录缺陷

使用团队现有的 P0/P1/P2/P3 级别，并描述用户可见后果。

每个问题至少包含：

- 受影响的路由或组件；
- 视口和应用状态；
- 证据（截图或可复现观察）；
- 可见症状；
- 可能原因，并明确标注已确认还是推测；
- 用户影响；
- 最小合理修复方案。

合并由同一个根因造成的重复问题，避免换一种描述重复报错。

### 5. 在授权范围内修复

任务允许修复时：

1. 只修复获派前端文件中的实质性偏差。
2. 保留已批准的视觉方向和设计令牌。
3. 尽可能一次修正一个明确问题，便于验证。
4. 不因视觉修复而安装依赖、改变产品行为、重设计无关页面或修改后端契约。
5. 如果缺陷来自 API/数据契约、后端行为或系统架构，应携带证据交给队长或后端架构师，不要在前端用掩盖问题的方式绕过根因。

### 6. 重新验证

- 使用发现缺陷时相同的路由、视口、状态和数据条件重新检查。
- 捕获修复后的截图，与原始基线或参考图对照。
- 确认修复没有引入新的溢出、重叠或状态回归。
- 修复后仍存在的问题不得报告为已解决；应重新判断原因或列为遗留问题。
- 修复次数应有边界。如果下一步需要新的设计决策、更大范围重构或后端变更，应停止并升级处理。

## 五、与代码审查的边界

本 Skill 判断真实渲染界面是否存在用户可见的视觉或交互缺陷，不负责证明通用代码正确性、安全性、后端契约或可维护性。这些事项由 `independent-code-review-workflow` 或 `backend-architecture-workflow` 处理。

UI 工程师负责视觉方向。Reviewer 可以独立核对证据和功能正确性，但不得用个人审美替换已批准的视觉方向。

## 六、交付格式

简洁报告：

- 检查范围与路由；
- 实际检查的视口和状态；
- 证据引用；
- 缺陷与严重程度；
- 已实施的修复；
- 修改前后验证结果；
- 剩余偏差和受阻检查。

没有实际检查的视口、状态、截图比较或浏览器交互，不得声称已经检查。
