# 视觉方向与设计系统提取

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

### 1. 视觉方向：确定界面设计语言

适用于用户或队长要求确定视觉风格、主题、设计语言或新界面方向的情况。

1. 阅读项目现有品牌规范、`design.md`、`design-system.md`、主题配置和代表性页面。
2. 判断当前界面属于产品工具界面（管理后台、仪表盘、设置页、开发者工具等），还是营销与品牌展示界面。产品工具优先考虑清晰度、信息扫描效率、有效密度和任务完成效率；营销界面则考虑叙事和转化。
3. 用简洁语言说明视觉主张：目标气质、材质感、信息密度和产品个性。
4. 只定义当前页面真正需要的设计决策：
   - 颜色角色与设计令牌；
   - 字体角色与字号层级；
   - 间距与布局节奏；
   - 圆角、边框、阴影和表面层次；
   - 导航与内容布局；
   - 组件外观和交互状态。
5. 保持设计方向统一。避免直接套用通用模板、无意义装饰、过量卡片、滥用渐变和缺乏产品特征的 AI SaaS 风格。
6. 如果需要改变品牌定位、产品行为或重大交互决策，应将未决事项提交队长或用户裁决，不得擅自决定。

输出简洁的视觉方向说明或实施约定。设计方向确定并不代表实际渲染结果已经符合要求。

### 2. 设计系统提取：理解项目已有规范

适用于梳理、记录或扩展现有前端设计系统的情况。

1. 找到当前构建和运行环境真正使用的主题来源，不要只看未被引用的令牌声明。
2. 检查相关设计令牌、全局样式、组件库配置、局部覆盖规则和典型组件用法。
3. 只盘点当前任务相关的组件和模式。
4. 记录实际生效的值、约定、例外和不一致之处。项目已有设计系统时，不要另起一套互相竞争的规范。
5. 如果源码声明与实际渲染表现冲突，应使用项目配置的视觉工具核实，并报告差异。
6. 只有在用户要求或后续工作确实需要时，才新增 `design-system.md` 或专项设计说明。数值清单优先采用简洁、可机器读取的格式；设计理由和人工决策使用 Markdown。

## 三、工程原则

- **先尊重项目现状：** 已有产品决策和实际实现优先于通用设计建议。
- **视觉层级服务于任务：** 优先呈现用户需要的信息和操作；装饰必须有明确作用。
- **一致性允许合理例外：** 优先使用共享令牌和组件；确有理由的例外应明确记录。
- **抽象应解决真实问题：** 组件和工具应减少实际重复或复杂度，避免只转发属性的薄封装。
- **响应式必须有证据：** 检查项目支持的真实视口和内容条件，不能只凭一张桌面截图判断。
- **交互应具备可访问性：** 使用语义化控件、可见焦点、键盘操作、足够对比度和恰当标签。
- **不得虚报验证：** 源码检查、Lint、类型检查或构建通过，都不能单独证明真实页面正确。
