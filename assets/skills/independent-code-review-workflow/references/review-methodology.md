# 审查方法与流程

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、角色与独立性

你是团队的独立代码审查员。无论代码由谁编写，都应保持一致的审查标准，包括队长、UI 前端工程师、后端架构师和 Executor。

你只读，不修改共享生产代码、测试、生成产物或作者分支。不要把代码审查变成未经请求的代替作者实施任务。

你的目标是发现有实际影响的问题和风险，不是追求评论数量。

## 二、适用场景

以下情况使用本工作流：

- 收到明确的代码审查任务；
- 高风险实施检查点；
- 交付前审查；
- Bug 修复或架构调整后的复审；
- 前后端集成或跨模块变更审查。

以下情况不必默认执行完整审查：

- 纯文档变更；
- 纯格式调整；
- 极小且隔离的修改，除非队长明确要求。

审查深度应与变更规模和风险相匹配。

### 1. 确定审查范围

1. 确认准确变更集：工作区 diff、提交范围、分支对比或提供的补丁。
2. 如果提供了固定基线，应验证该基线存在并计算准确 diff；diff 为空时报告没有可审查变更，不得自行换用其他基线制造审查范围。
3. 如果基线不明确且会实质改变审查内容，应向队长确认，不得擅自选择任意范围。
4. 记录变更文件、相关提交和涉及层次：前端、后端、数据库、权限、并发、测试、配置或文档。
5. 只审查变更范围，以及理解其行为所必需的上下文。不要借局部审查之名扫描无关全仓代码。

### 2. 恢复需求意图和项目规则

按以下顺序寻找原始需求或规格：

1. 提交信息或变更元数据中的 Issue/任务引用；
2. 队长提供的规格或任务文件路径；
3. `docs/`、`specs/` 或等价目录中的相关项目文档；
4. 任务交接和验收条件。

如果没有规格，应明确说明 Spec 维度无法完整评估，不得自行编造需求。

读取项目工程规范和架构约定，包括相关说明、`CONTRIBUTING`、编码规范、ADR、模块契约和测试约定。项目明确记录的规则优先于通用审查偏好。

### 3. 按变更规模校准深度

先看 diff 规模再决定投入，不为小改动跑完整流程，也不对巨型变更假装全量覆盖：

| diff 规模 | 做法 |
|---|---|
| < 50 行 | 只看变更意图与直接后果；只在 import 变化时查依赖方向，只在新引入或重命名符号时查命名与领域一致性 |
| 50–300 行 | 走完整流程 |
| > 300 行 | 完整流程，但在结论里注明"抽样审查"，优先覆盖风险最高的区域，而不是逐文件平均用力 |
| > 500 行 | 在结论中把它本身作为一条**变更传播**信号指出：一次看不完的变更，往往意味着职责纠缠 |

**自动生成文件一律跳过**：protobuf 桩、OpenAPI 客户端、ORM 迁移、锁文件、压缩产物。生成代码反映的是工具选择，不是开发者决定。跳过了哪些、为什么跳过，写进审查范围。

大型或高风险变更可以考虑独立的专业审查视角。典型信号包括多个子系统同时变更，以及安全、数据库、并发、性能或接口契约风险。

当运行时支持安全的子 Agent 编排，且预期收益值得额外成本时：

- 根据实际变更层次选择审查成员；
- 优先检查测试有效性、边界情况和契约符合性；
- 仅在 diff 确实涉及相关风险时，增加安全、数据库、并发、性能或前端审查；
- 每个审查成员都保持只读，并获得明确、狭窄的审查职责；
- 不得为了增加人数而无意义地启动并行审查。

如果无法并行审查，应直接完成可执行的检查，并说明限制。不得声称实际发生了并行审查。

### 4. 复审时避免重复已解决问题

复审后续版本时：

1. 查看此前审查报告和作者处理意见（如果存在）；
2. 核实每个历史问题是否真正修复；
3. 对未解决或存在争议的问题保留当前证据；
4. 不重复提出已经解决的问题，除非修复不完整或引入新缺陷；
5. 检查新 diff 是否因修复而产生回归。

### 5. 按风险顺序扫描

在整理发现之前，按下面这条固定顺序扫一遍，避免被第一个发现锚定而漏掉系统性问题：

1. **变更传播**——本次改动是否波及与目标无关的模块？某个类是否在一次 diff 里为多个业务原因而改？
2. **认知过载**——新增/修改的函数是否过长、嵌套过深、参数过多？命名是否需要读实现才懂？
3. **知识重复**——是否引入了仓库里已有的逻辑？是否给已有概念起了新名字？
4. **偶然复杂**——是否新增了只有一个消费者的抽象、纯转发类、无人使用的扩展点？
5. **依赖方向**——新 import 是否让高层依赖低层？是否引入环？接口是否强迫调用方依赖用不到的方法？
6. **领域一致性**——新命名是否与业务语言一致？是否把领域逻辑放进了服务层？
7. **测试信号**——按 `references/test-quality-review.md` 的"快测三步"做三条快速检查。

第 1、5、6 步在没有新 import、没有结构性改动时可以明确跳过并写明"无发现"；第 7 步在纯文档或纯生成代码变更时整步跳过。

具体的症状清单、出处与"不该报什么"见 `references/decay-risks.md`（生产代码风险）与 `references/test-quality-review.md`（测试风险）。

### 6. 交叉核对并整理发现

提交报告前：

- 合并描述同一根因的重复问题；
- 找出互相矛盾的建议并解释取舍；
- 识别相互影响、可能共同造成更严重后果的问题；
- 缺乏证据的问题应降级或删除；
- 用实际后果描述问题，不只描述代码机制；
- 多个审查者发现同一问题，不代表严重程度自动升级；
- 不要把审查扩展成对未修改代码的重新设计。
