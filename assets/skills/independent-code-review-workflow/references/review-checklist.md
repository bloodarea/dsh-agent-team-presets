# 项目规范、需求与测试检查清单

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、沿两个独立维度审查

两个维度必须分开。代码可能通过其中一个维度，却在另一个维度存在问题。

#### 维度 A：Standards（项目规范）

检查 diff 是否符合项目已记录的约定和架构。

根据变更检查：

- 命名、可读性、内聚性、重复和可维护性；
- 模块职责、接口复杂度、依赖方向和局部性；
- 错误处理、资源生命周期和可观测性；
- 安全、权限、输入校验和密钥处理；
- 并发、事务、重试和数据完整性；
- 前端状态与渲染生命周期、响应式行为；
- 兼容性、迁移和项目特有模式。

代码异味只是审查线索，不自动构成违规。项目明确约定优先于通用偏好。Lint 等自动检查已经覆盖的问题，不要重复报告，除非自动检查配置本身存在错误。

#### 维度 B：Spec（需求符合性）

检查变更是否准确实现了要求的行为。

重点检查：

- 必须实现的行为是否缺失或只完成了一部分；
- 看似实现但实际行为错误的部分；
- 需求未覆盖的重要边界和失败路径；
- 超出需求范围或未经请求的行为；
- 与 API、数据或状态契约不一致；
- 必要的用户可见状态是否缺失。

尽可能引用相关需求或规格。不要将 Standards 和 Spec 混成一个分数。

## 二、验证测试是否有效

不要仅凭测试套件全绿就认定代码正确。

对相关测试检查：

- 测试是否真正经过被修改的代码路径；
- 初始化和测试数据是否代表相关条件；
- 如果目标缺陷存在，断言是否会失败；
- 重要的负向、边界和错误路径是否覆盖；
- Mock 是否替代了本应验证的集成或真实行为；
- 测试是否稳定，是否依赖偶然的执行顺序或共享状态。

只有在允许且安全时才运行测试。独立执行前确认不会修改共享状态、消耗一次性资源或干扰其他 Agent。明确区分已阅读的测试和实际运行的测试。
