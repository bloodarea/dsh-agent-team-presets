# 测试质量审查（T1–T6）

> 本文是主 Skill 的按需参考资料。仅在变更包含测试、或需要判断"测试是否真能捕获该缺陷"时读取。

先区分两件事：**测试存在** 与 **测试有效**。全绿不等于真实验证；行覆盖率衡量的是执行，不是验证。

## 风险清单

### T1 测试晦涩
**诊断问题：** 看一条测试，要花多少力气才能知道它验证什么？
- 症状：断言轮盘（多个断言没有提示信息，失败时分不清是哪条行为坏了）；神秘访客（依赖测试体内看不见的外部状态：文件、库表行、环境变量、共享可变夹具）；测试名不表达场景与预期（`test1`、`shouldWork`、`testLogin`）；通用夹具（一个过大的 setUp / beforeEach 被互不相关的测试共享，每个测试的前置条件因此不可见）；读懂测试体必须先读生产代码。
- 出处：Meszaros《xUnit 测试模式》Assertion Roulette / Mystery Guest / General Fixture；Osherove《单元测试的艺术》命名约定。
- 严重度：文件中没有任何测试名描述被测行为、所有断言无提示 → P1；多处神秘访客、若干含糊测试名 → P2；命名零散问题、孤立通用夹具 → P3。
- **不该报**：多个断言共同描述一条连贯行为、且失败时故事清晰，可以接受；每个初始化值都与几乎所有测试相关时，共享 setUp 是合理的。

### T2 测试脆弱
**诊断问题：** 重构但不改变行为时，测试会不会挂？
- 症状：断言私有方法结果、内部状态或实现细节；急切的测试（一条测试验证多个互不相关的行为，任何一处变更都让它失败）；过度指定（断言与行为无关的 mock 调用顺序或精确参数）；重命名或抽取方法导致 5 条以上测试失败但行为没变；不稳定测试（同样的代码在不同轮次结果不同，源于竞态、时间依赖、随机数据或测试间共享可变状态）。
- 出处：Meszaros Eager Test / Erratic Test；Osherove 测试隔离；Hunt & Thomas 正交性。
- 严重度：无行为变更的重构导致测试失败，或 5 条以上测试耦合同一实现细节 → P1；急切测试普遍、存在中等程度实现细节断言 → P2；非关键测试里孤立过度指定 → P3。
- **不该报**：验证外部可观察事件或发出的命令不是实现耦合；一条测试的多个断言都支持同一行为主张时可以接受；仍断言行为而非接线的内存适配器不是脆弱。

### T3 测试重复
**诊断问题：** 同一个测试场景是不是写了好几遍？
- 症状：相同的 setup 或断言逻辑复制粘贴到多个测试而没有抽取；惰性测试（多条测试验证同一行为，输入、状态、预期没有任何区别）；同一边界条件在单元/集成/E2E 三层各测一遍且无层次差异；测试辅助函数或夹具在多个测试文件里各存一份。
- 出处：Meszaros Test Code Duplication / Lazy Test；Hunt & Thomas DRY。
- 严重度：核心业务场景在三个层完整重复且无差异 → P1；常见场景 setup 在 5 条以上测试中重复 → P2；少量辅助函数重复、孤立惰性测试 → P3。
- **不该报**：同一场景在单元层与集成层各出现一次、但各自验证不同风险，是合理的；小范围局部 setup 重复有时比过度抽象的夹具迷宫更清楚。

### T4 Mock 滥用
**诊断问题：** 测试是不是比它要验证的行为还复杂？
- 症状：mock 搭建代码比测试逻辑还长；主要断言是 `expect(mock).toHaveBeenCalledWith(...)`——验证的是 mock 被调过，而不是真的发生了什么；为测试生命周期往生产类里加只被测试调用的方法（测试诱导的设计损伤）；单个单元测试用了 3 个以上 mock；不完整的 mock（缺少下游要访问的字段，失败只在集成时才暴露）；硬编码测试数据与真实数据形状或约束毫无关系。
- 出处：Meszaros Behavior Verification / Hard-Coded Test Data；Osherove mock 使用与完整性要求；Feathers 感知与分离。
- 严重度：mock 搭建超过测试代码一半，或生产类存在只被测试调用的方法 → P1；每条测试普遍超过 3 个 mock、主要断言是 mock 调用 → P2；孤立的不完整 mock、轻微硬编码数据 → P3。
- **不该报**：围绕非确定性依赖用少量 mock、而断言仍验证行为，可以接受；用来观察状态迁移的 fake 与 spy 不默认算滥用；当"交互本身"就是被测行为时，一条交互断言是恰当的。

### T5 覆盖假象
**诊断问题：** 这套测试真的挡住了要紧的失败吗？
- 症状：行覆盖率高，但错误处理分支、边界条件、异常路径没有对应测试；只有快乐路径，没有 null/空/0 输入与并发边界；正在被改的遗留区域没有测试（"遗留代码就是没有测试的代码"）；把覆盖率当作放行标准，而关键变更路径仍未测；只断言返回值，不断言数据库写入、事件发布、状态迁移等重要副作用。
- 出处：Feathers 第 1 章；《Google 软件测试之道》变更覆盖与行覆盖之别；Osherove 完整性原则。
- 严重度：正在改的遗留区域完全没有测试，或错误处理路径整体缺席 → P1；覆盖率 > 80% 但边界与异常路径系统性缺失 → P2；少数非关键路径缺失败路径测试 → P3。
- **不该报**：行覆盖率高且有分支、边界、变更路径覆盖时，高覆盖率是有用的；新模块在仍是私有且低风险时覆盖率有限可以接受；副作用断言放在集成测试里不代表有缺口。

### T6 架构错配
**诊断问题：** 测试套件的结构是否反映了系统真实的风险分布？
- 症状：测试金字塔倒置（E2E 或集成测试数量超过单元测试），套件又慢又脆；遗留代码没有接缝——没有接口、依赖注入或可替换点，不修改生产代码就无法隔离测试；正在改的遗留区域在改动前没有特征测试（Characterization Test）锁住当前行为；整套测试运行超过 10 分钟；高风险与低风险路径测试密度相同，没有按风险分配。
- 出处：《Google 软件测试之道》70:20:10；Feathers 接缝模型与特征测试；Meszaros 缓慢测试。
- 严重度：正在改的遗留代码既无接缝也无特征测试、金字塔完全倒置 → P1；套件运行 > 10 分钟、集成/E2E 数量超过单元测试 → P2；局部比例偏离、少数遗留区域缺特征测试 → P3。
- **不该报**：70:20:10 的偏离可以被平台约束或产品风险合理说明；集成测试为主的套件只要反馈快、分层有意，仍然健康；少量关键路径 E2E 是期望的，不是异味。

## 特征测试的最小写法

改动不清晰的既有行为之前，先锁住它当前的表现——对或错都锁：

```
test("characterize: [模块].[方法] 给定 [输入]，返回 [当前输出]") {
  // 用真实形状的输入调用被测代码
  // 断言它当前实际返回什么，即使你怀疑它不对
  // 注释注明：这里记录的是当前行为，不是正确行为
}
```

## 快测三步（PR 审查场景专用）

变更包含测试文件时，只做三条快速信号，不做完整测试诊断：

1. **有没有测试？** 改动生产代码却没有任何测试变更，而新公开行为没有新测试 → `覆盖假象`（P2）。
2. **mock 比例？** mock 搭建明显长于测试逻辑、主要断言是 mock 被调用、或生产类新增了只被测试调用的方法 → `Mock 滥用`（P2；后者可升 P1）。
3. **测试名与断言？** 新测试名不表达场景与预期、多个断言且无提示信息 → `测试晦涩`（P3）。

三条信号都干净时不写测试类发现，也不要为了凑数引进。
