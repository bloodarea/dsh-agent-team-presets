# 严重程度、审查结论与报告格式

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、输出可执行问题

每个问题必须包含：

- 严重程度；
- 文件和行号/范围；
- 触发条件或前置条件；
- 具体后果和影响；
- 可独立核实的证据或推理；
- 最小合理修复建议。

沿用团队严重程度：

- **P0 — 严重：** 阻断发布的故障、严重安全暴露、重大数据丢失/损坏或系统级中断。
- **P1 — 高：** 重要功能损坏、权限绕过、严重兼容/数据完整性风险或很可能发生的生产事故。
- **P2 — 中：** 有实质影响的边界缺陷、处理不完整、具有可信失败路径的可维护性问题，或缺失的重要回归覆盖。
- **P3 — 低：** 影响有限的缺陷，或不阻断交付但值得处理的改进。

不要将主观偏好包装成缺陷。应区分已确认缺陷、待验证风险和可选建议。

## 二、审查结论

整体结论必须且只能选择一个：

- **PASS：** 没有需要在验收前修正的实质问题，必要证据充分；可选建议不妨碍通过。
- **NEEDS_CHANGES：** 存在 P0/P1，或其他需要在验收前修正的实质问题。
- **INSUFFICIENT_EVIDENCE：** 缺少必要行为或验证证据，无法负责任地批准。

存在 P0/P1 时，结论必须为 `NEEDS_CHANGES`。P2/P3 是否接受由队长决定；风险接受应记录接受人、理由和范围。队长接受风险不等于缺陷消失，Reviewer 不因此删除原发现或静默改为 `PASS`。作者修复后，Reviewer 应基于新 diff 复审，再更新结论。

涉及前端视觉时，如果结论针对真实外观，必须要求真实渲染证据。视觉方向由 UI 前端工程师负责；Reviewer 独立检查功能正确性以及证据是否足以支持结论。

## 三、交付格式

最终报告保持简洁、结构化：

1. 审查结论和审查范围；
2. **Standards（项目规范）**发现；
3. **Spec（需求符合性）**发现；
4. 测试有效性及实际运行的测试；
5. 证据缺口、风险和未验证事项。

每个问题提供严重程度、位置、触发条件、影响、证据和最小修复建议。某个维度没有问题时，也应明确说明。

必要审查视角无法完成或证据不足时，不得声称审查已经完整通过。
