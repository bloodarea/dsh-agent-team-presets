# 代码衰减风险清单（R1–R6）

> 本文是主 Skill 的按需参考资料。仅在审查生产代码、跨模块变更或架构性缺陷时读取；不要默认加载。

每条风险按四段式记录：**症状（看到什么）→ 出处（哪条工程原则）→ 后果（不修会怎样）→ 最小修复**。
这套结构的作用是防止"只列规则违反、不说明为什么重要"的空洞审查。

> **硬约束：** 未完成诊断前不要先给修复方案。一条没有后果和修复方向的发现不是发现，是噪音。

## R1 认知过载

**诊断问题：** 读懂这段代码需要人记住多少东西？

- 症状：函数同时混合多个抽象层次；嵌套超过 3 层；参数超过 4 个；出现无从解释的魔数；变量名必须读实现才懂（`d`、`tmp2`、`flag`）；布尔参数让一个函数干两件不同的事（Flag Argument，说明职责有两份）；领域概念用裸类型承载（`String email`、`int orderId`），调用方得自己记住哪个是邮箱；浅模块——接口比它提供的能力还复杂。
- 出处：Fowler《重构》Long Method / Long Parameter List / Message Chains / Flag Argument / Primitive Obsession；McConnell《代码大全》第 7、11、12 章；Evans《领域驱动设计》统一语言；Ousterhout《软件设计哲学》第 4 章（深模块）。
- 后果：执行者理解成本上升，改动更容易带出错误，且没人愿意碰它。
- 严重度参考：函数 > 50 行、嵌套 > 5 层、几乎没有有意义命名 → P1；20–50 行、嵌套 4–5 层、部分命名不清 → P2；零散命名问题、个别魔数 → P3。

**不该报什么**
- 命名清晰、用守卫子句展开的平铺代码，本身不是高认知负荷。
- 藏在深而简单的模块接口后面的实现细节，不是浅模块问题。
- 与领域专家实际说法一致的术语，不因"看起来不通用"而报。

## R2 变更传播

**诊断问题：** 改一处，会连带弄坏多少不相干的东西？

- 症状：改一个功能要动 3 个以上无关联模块的文件；同一个类为多个不同业务原因而改（计费、通知、资料混在一起）；一个方法用别的类数据比用自己的还多；两个类互相知道对方内部状态；**Hyrum 定律**——调用方足够多时，任何可观察行为（包括实现细节、报错文案、偶然的调用顺序、未写入文档的副作用）都会变成事实契约；**正交性破坏**——改一个维度被迫动无关维度（加一种支付方式却要改日志、缓存、通知）；**信息泄漏**——一个设计决定（文件格式、协议细节、数据形状）被编码在多个模块里。
- 出处：Fowler Shotgun Surgery / Divergent Change / Feature Envy / Inappropriate Intimacy；Hunt & Thomas 正交性；Martin 依赖倒置；Brooks《人月神话》第 2 章（沟通成本即传播半径）；《Google 软件工程》Hyrum 定律；Ousterhout 信息隐藏与泄漏。
- 后果：回归面扩大，单次变更成本随调用方数量超线性增长。
- 严重度参考：一次变更涉及 > 5 个文件，或出现结构性的依赖倒置（领域依赖基础设施）→ P1；3–5 个文件、轻度耦合 → P2；耦合轻微且易隔离 → P3。

**不该报什么**
- 组合根（composition root）装配具体依赖，本身不算依赖倒置违规。
- 明确承诺支持的稳定公开 API，不自动构成 Hyrum 定律债务。
- 同一限界上下文内的相似改动可能是正常的协同变更，不是 Shotgun Surgery。

## R3 知识重复

**诊断问题：** 同一个决定，是不是被写在了好几个地方？

- 症状：同一段逻辑在多个文件里复制；同一概念在不同地方叫不同名字（`user` / `account` / `member` / `customer` 指同一实体）；两条平行类层次必须同步演化；配置值以字面量在多处重复；两个模块各自实现了同一算法。
- 出处：Fowler Duplicate Code / Parallel Inheritance Hierarchies / Alternative Classes with Different Interfaces；Hunt & Thomas DRY；Evans 统一语言。
- 后果：副本之间会静默漂移，改一处忘一处的概率随份数上升。
- 严重度参考：核心业务逻辑跨模块重复，或同一领域概念有 3 种以上叫法 → P1；工具代码重复、子系统内命名不一致 → P2；零散字面量重复 → P3。

**不该报什么**
- 不同限界上下文之间的重复，不自动等于重复知识。
- 正在进行的抽取或迁移期间的临时重复，不一定已经成为债务。
- 协议常量在明确边界上各自声明，有时比抽象成共享常量更清晰。

## R4 偶然复杂度

**诊断问题：** 代码是不是比它要解决的问题更复杂？

- 症状：为"将来可能用到"建的抽象，当前没有消费者（只有一个实现的插件系统）；几乎没有存在理由的类（包了一层单个方法调用）；只做转发的纯中间人；**二次系统效应**——第二版比第一版庞大得多，为尚不存在的需求加通用性；switch 语句暗示缺少多态；从未被改过的配置项；框架代码比它驱动的应用还大；长期战术性捷径累积成"每个新功能都要先跟现有结构搏斗"。
- 出处：Fowler Speculative Generality / Lazy Class / Middle Man / Switch Statements；Brooks 第 5 章二次系统效应；McConnell 第 5 章 YAGNI；Hunt & Thomas 好够用即可；Ousterhout 战略式与战术式编程。
- 后果：改动要先绕过脚手架，边际收益递减，执行者把精力花在维护结构而不是解决问题上。
- 严重度参考：整个子系统围绕一个假想需求建成，或框架开销压过领域逻辑 → P1；若干多余抽象/包装类、未使用的配置体系 → P2；非关键路径上一两个惰性类 → P3。

**不该报什么**
- 对外部协议、线格式或封闭枚举的 switch，不自动等于缺少多态。
- 吸收供应商变动或隐藏不稳定性的薄包装可能是合理的。
- 第二版更大不等于二次系统效应——除非新增的通用性超出了当前需要。

## R5 依赖失序

**诊断问题：** 依赖方向是否一致、可预测？

- 症状：模块或包之间循环依赖；高层业务逻辑直接 import 底层基础设施（领域服务 import 具体数据库驱动）；稳定、被广泛依赖的组件依赖不稳定、频繁变动的组件；抽象依赖具体实现；迪米特法则违规（`order.getCustomer().getAddress().getCity()`）；模块扇出超过 5；接口隔离违规——实现方只需用接口的一部分，或必须为不需要的方法提供桩实现；"这不像一个人设计的"——不同模块用互不兼容的架构模式且没有规则；对传递依赖直接版本钉死（菱形依赖），升一个库要协调多个团队。
- 出处：Martin 无环依赖 ADP / DIP / SDP / SAP / ISP / SRP / OCP；Brooks 第 4 章概念完整性；Hunt & Thomas 解耦与迪米特法则；《Google 软件工程》第 21 章依赖管理。
- 后果：基础设施变更级联进领域层；循环让隔离与替换变得不可能。
- 严重度参考：存在依赖环，或领域层直接依赖基础设施层 → P1；多处 SDP/DIP 违规但无环、模块间概念不一致 → P2；轻微迪米特违规、孤立模块扇出偏高 → P3。

**不该报什么**
- 编排层或组合根的高扇出，不自动算失序。
- 适配器模块同时依赖领域与基础设施，只要它明确在边界上做转换，是正常的。
- 覆盖多个叶子依赖的稳定门面，只要依赖策略清晰，是健康的。

## R6 领域模型失真

**诊断问题：** 代码是否忠实表达了它要解决的问题？

- 症状：业务逻辑散落在服务层，领域对象只有 getter/setter（贫血领域模型）；代码中的类/方法名与业务方对同一概念的说法不一致；类的唯一职责是装数据、没有行为（纯数据袋）；子类忽略或覆盖掉父类大部分行为（拒绝继承的馈赠）；跨限界上下文却不做任何转换或防腐层；方法对别的类的数据比对自己的更感兴趣（领域逻辑错位）；子类以不兼容行为覆盖父类、或在父类承诺成功的地方抛出异常（LSP 违规）；值对象被当成实体——本应由属性完全定义的概念（Money、Email、Address）被赋予可变 ID 和生命周期。
- 出处：Evans 领域模型 / 统一语言 / 限界上下文；Fowler Data Class / Refused Bequest / Feature Envy；Martin LSP。
- 后果：读代码要先在心里做一次翻译，模型逐渐变成对着表结构画皮。
- 严重度参考：领域逻辑全在服务层，领域对象是纯数据袋 → P1；部分贫血、命名与领域语言有明显出入 → P2；非核心区域轻微命名漂移、孤立 Feature Envy → P3。

**不该报什么**
- CRUD 密集的流程可以合理地用事务脚本，而不是富领域对象。
- DTO、持久化记录、API 载荷模型允许是纯数据。
- 业务模型本身简单时，共享基础设施语言不应被误判成领域漂移。

## 使用方式

1. 按上表逐条扫描变更涉及的范围，只报**在本次变更中确实可见**的风险。
2. 每条发现给出：风险编号与名称、文件与行号/范围、触发条件、后果、最小修复方向。
3. 先按严重程度排序（P1 → P2 → P3），再在同类内部按影响面排序。
4. 结论只有三种：`PASS`、`NEEDS_CHANGES`、`INSUFFICIENT_EVIDENCE`；存在 P1 时必须是 `NEEDS_CHANGES`。
