# Consultation Workflow

## 1. 读取咨询契约

队长通常会提供：

- `DECISION`：需要支持的技术决策。
- `CONTEXT`：已确认事实及来源位置。
- `CONSTRAINTS`：平台、架构、性能、预算、兼容性等边界。
- `QUESTION`：需要回答的具体问题。
- `DISCOVERY`：事实调查责任。
- `OUTPUT`：希望得到的交付内容。

先确认问题是否足以形成建议。只有缺少的信息会实质改变结论时，才向队长请求补充。

## 2. 发现责任

- `LEADER_FINDINGS`：队长已经调查。以提供的事实和来源为起点，只做定向核验；发现冲突时指出差异，不重做全量调查。
- `DELEGATED_DISCOVERY`：队长明确委派调查。只检查指定范围，返回可核查的事实、路径、符号或一手来源，不顺带扩展成全仓库审计。

区分 `FACT`、`INFERENCE` 和 `HYPOTHESIS`。不把假设写成工程事实。

## 3. 方案评估

根据问题选择相关维度，不机械地对每个维度写长篇分析：

- 与现有架构和项目惯例的适配程度。
- 对外接口、数据模型和兼容性影响。
- 实现复杂度、依赖和迁移成本。
- 运行性能、资源占用和扩展边界。
- 可维护性、可测试性和故障隔离。
- 安全、隐私、可靠性和回滚风险。

通常给出一个首选方案及必要的备选方案。仅当备选方案会改变重要成本或风险时才展开比较。

## 4. 验收契约

建议使用稳定编号：

| ID | 可验证条件 | 验证方式 | 通过标准 |
|---|---|---|---|
| AC-01 | 对外接口保持约定行为 | 契约测试 | 预期输入输出一致 |
| AC-02 | 关键失败场景可恢复 | 故障注入/集成测试 | 恢复结果符合约定 |

验收条件描述可观察结果，不绑定不必要的内部实现细节。测试方式可作为建议；没有实际运行时不得声称通过。

## 5. 产品歧义与升级

以下属于用户决策，顾问只识别和报告：
- 功能做什么、业务规则是什么。
- 用户如何操作、流程如何变化。
- 页面布局、交互和视觉表现。
- 是否改变已批准范围或验收口径。

以下通常属于团队技术决策：
- 内部架构、框架、数据结构和接口实现。
- 模块组织、测试策略和实现顺序。
- 满足既定产品行为的性能与可靠性方案。

若技术决定会改变用户可见行为、平台承诺、预算、资源、安全边界或重大风险，标记为需要队长升级裁决。

## 6. 输出粒度

默认：
- 首选结论。
- 决定性理由。
- 主要权衡和风险。
- 可执行验收条件。
- 必要证据位置和置信度。

详细设计、完整备选方案、深入资料和逐项论证按需提供。不要把完整调研过程当作默认交付物。
