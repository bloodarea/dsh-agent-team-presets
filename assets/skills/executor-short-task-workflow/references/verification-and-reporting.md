# Verification & Reporting

## 按风险选择验证

优先使用项目已有且与修改相关的验证手段。

| 修改类型 | 优先验证 |
|---|---|
| 文案或注释 | Diff 检查及项目已有的格式/链接检查 |
| 局部业务逻辑 | 对应单元测试、边界条件 |
| 模块接口或数据结构 | 契约测试、调用方兼容性、相关集成测试 |
| 跨模块修改 | 受影响模块测试及关键集成路径 |
| 构建、依赖或配置 | 对应构建、启动或配置校验 |
| 用户可见交互 | 相关 UI 测试或可复现的人工验收步骤 |
| 安全或数据处理 | 针对风险的专项验证 |

验证范围与修改风险匹配。优先运行最相关的测试，再根据失败或影响扩大验证范围。

## 验证结果

- `PASS`：命令实际运行且通过。
- `FAIL`：命令实际运行但失败。
- `NOT RUN`：未运行，并说明原因。
- `BLOCKED`：因环境、权限或依赖无法执行。
- `NOT APPLICABLE`：不适用于本次修改，并说明依据。

测试命令、关键输出摘要和环境限制应足以让队长复核。避免粘贴无关长日志或敏感数据。

## 发给队长的结果契约

```text
STATUS: DONE | PARTIAL | BLOCKED | FAILED
TASK_ID: <when assigned>
CHANGES:
- <file/path or symbol>: <concise outcome>
TESTS:
- <command/check>: PASS | FAIL | NOT RUN
BLOCKERS: <NONE or required decision>
```

只报告当前任务相关信息。队长已知背景不重复转述。

## 完成判断

代码修改完成、测试通过和用户需求验收是不同层次。执行者报告实际实现和验证状态；队长结合整体需求判断工作项是否通过最终验收。发现额外问题时提供路径、现象和影响，等待队长决定是否新增任务。
