# Product Alignment：产品需求对齐

## 决策分类

**用户裁决的产品事项**
- 功能：做什么、业务规则、输入输出、边界条件和异常行为。
- 用户流程：从哪里进入、执行哪些操作、如何完成目标。
- 界面：页面结构、主要区域、关键组件、交互方式和重要视觉预期。
- 范围：本次交付包含什么、不包含什么。
- 验收：如何判断最终产品符合预期。

**团队自治的技术事项**
- 架构、框架、数据库、内部接口和数据结构。
- 模块边界、代码组织、依赖注入和设计模式。
- 测试层次、自动化方式、构建与部署实现。
- 满足已批准产品要求的技术路线和实施顺序。

## 启动前澄清重点

| 领域 | 需要明确的内容 |
|---|---|
| 功能 | 功能清单、业务规则、输入输出、异常行为 |
| 流程 | 主要操作路径、页面跳转、关键状态变化 |
| 界面 | 页面结构、关键组件、交互和重要视觉要求 |
| 范围 | 本次交付与明确排除项 |
| 验收 | 可观察的成功条件和重要失败条件 |

不必提前确定每个像素、CSS 属性或所有微交互；重点是用户和团队对产品结果形成一致理解。

## 多轮澄清方法

1. 队长提交对目标的理解和已知约束。
2. 将影响产品行为的未决问题归组，集中提问。
3. 对抽象问题提供具体选项、示例流程或低保真原型。
4. 记录用户选择及其影响。
5. 更新需求基线，再处理下一组关键歧义。

允许分多轮完成。未影响当前阶段的远期细节可以保留为待确认事项。

## 需求基线

首轮实现前，至少记录 Objective、Functional Scope、User Flow、Interface Expectations、Constraints、Acceptance Criteria 和 Open Questions。会影响当前交付正确性的功能或界面问题应先澄清；仅影响远期阶段的问题可在该阶段开始前解决。

## 基线变更

用户提出新需求或批准范围变化时，记录变更内容、原新基线差异、对交付物/进度/依赖/验收的影响及批准情况。不得将团队自行选择的技术实现写成用户已确认的产品需求。
