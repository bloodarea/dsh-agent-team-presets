# Leader Long Task Orchestration

## 目标

管理长程任务完整生命周期：用户确定产品方向和边界，团队自主决定技术实现，Agent 在批准基线内持续执行并交付可核验结果。

## 触发判断

任务具有多阶段交付、显著依赖、多轮执行、较高不确定性或需要跨会话跟踪时使用。短程任务直接派发；有界中程任务使用 `leader-medium-task-workflow`。

## 核心流程

1. **理解需求**：提炼目标、预期功能、用户流程、界面要求、范围和约束；进入工程探查后，若存在多个独立调查方向，必须调用 `agent-subagent-orchestration` 并行探查。
2. **分类歧义**：功能与界面歧义属于产品决策，应在相关实现启动前与用户对齐；普通技术歧义由团队讨论决定。
3. **多轮对齐**：允许分多轮澄清。使用例子、流程或低保真原型解释关键产品选择，不要求首次确定全部计划。
4. **团队技术决策**：队长组织执行者和 `fullstack-advisor` 评估方案，记录重要决定及理由。顾问按需介入，只提交决策摘要与验收契约。
5. **建立基线**：将用户确认的目标、功能、界面预期、范围、约束和验收原则写入持久化 `DELIVERY-PLAN.md`。用户批准基线及首轮计划后启动执行。
6. **滚动规划**：当前轮次细化到可执行任务；下一轮明确目标、交付物和依赖；远期阶段保留方向和待确认事项。计划随新事实更新。
7. **分轮执行**：每轮使用宿主 Team Task Board 分派成员任务，队长 Todo 管理自己的协调动作。执行者按 `executor-short-task-workflow` 完成有界工作项。
8. **阶段验收**：核对交付物、证据和产品基线，更新计划文档中的验收状态、决策和下一轮安排。
9. **最终交付**：汇总整体完成度、未完成项、遗留风险和最终验收结果。

## 决策权

- 用户决定产品目标、功能行为、用户流程、界面预期、范围及重大变更。
- 团队决定符合已批准产品基线的架构、技术栈、内部接口、实现方式和测试策略。
- 技术变化若影响产品行为、范围、兼容性承诺、预算、资源、安全边界或交付承诺，提交用户裁决。
- 新出现的功能或界面歧义，暂停受影响部分并向用户确认；普通实现细节由团队处理。

## 计划与验收

- 每个长程任务维护一份持久化 `DELIVERY-PLAN.md`，作为目标基线、计划、决策和验收的唯一事实来源。
- 不要求一次性详细规划所有轮次；根据工程事实滚动细化。
- 验收统计分为已完成、部分完成、未完成；每项状态必须有定义和证据。
- 用户批准的产品基线变更需记录版本、原因和影响，不得静默改写原始需求。
