# 文档架构与目录治理规范

本文件定义 README、`docs/`、`docs/internal/` 的职责边界、公开文档目录和 Git 忽略规则。

## 一、三层文档体系

所有仓库统一采用三层文档职责。三层按**读者与信息用途**划分，不按文件格式或篇幅划分。

| 层级 | 位置 | 主要读者 | 核心职责 |
|---|---|---|---|
| 项目入口 | `README.md`、`README.zh.md` | 所有访问者、潜在用户 | 快速理解项目、判断价值、开始使用 |
| 公开文档 | `docs/` | 用户、集成开发者、外部贡献者 | 提供完整、准确、可依赖的使用与技术资料 |
| 内部文档 | `docs/internal/` | 项目维护者 | 保存研发过程、实验记录、内部计划和实现笔记 |

### 1. README：项目入口

README 是项目的 Landing Page，不是完整技术手册。

它应帮助读者快速回答：

1. 这是一个什么项目？
2. 它解决什么问题？
3. 它有哪些已经具备的核心能力？
4. 我如何快速运行或体验？
5. 如果需要深入了解，应该去哪里阅读？

README 只保留项目认知、价值判断、核心能力、最短上手路径和公开文档入口。详细配置、完整 API、架构细节、开发过程等内容应放在 `docs/` 或其他合适的公开文件中，并从 README 链接过去。

### 2. `docs/`：正式公开文档

`docs/` 保存面向外部读者的正式资料。它应描述**当前真实可用的项目行为、公开接口、稳定约定和明确能力边界**。

适合放入：

- 安装、配置、使用教程。
- 功能说明、使用场景和操作流程。
- 对外公开的系统架构、模块关系和数据流。
- API、协议、接口、数据格式与扩展规范。
- 兼容性、环境要求、能力矩阵和限制。
- 第三方集成、插件开发和贡献指南。
- 面向使用者的 FAQ 与故障排查。

公开文档应当可被外部用户独立理解，不依赖内部开发日志才能使用。

### 3. `docs/internal/`：本地内部文档

`docs/internal/` 专门保存维护者使用的研发过程资料，例如：

- 开发日志、阶段记录和迭代过程。
- 内部任务拆分、开发计划和临时里程碑。
- 技术调研、方案比较、实验记录与失败尝试。
- 尚未定稿的架构讨论和实现设计。
- 内部验收记录、测试过程、排障过程。
- 临时实现笔记、重构记录和维护者备忘。

内部文档允许保留过程性、探索性和未定稿内容，不要求像公开文档一样精简或稳定。

**内部文档不得成为公开文档的唯一事实来源。** 一旦某项接口、架构约定或能力说明需要对外使用，应将经过确认的结论整理到 `docs/` 的正式文档中，而不是要求外部读者查看内部记录。

## 二、内部文档必须被 Git 忽略

`docs/internal/` 是本地工作区目录，默认不进入公开 Git 仓库。

在仓库根目录 `.gitignore` 中添加：

```gitignore
# Local-only internal documentation; never commit
/docs/internal/
```

规则要求：

- 使用根目录锚定路径 `/docs/internal/`，只忽略当前仓库的内部文档目录。
- 不要在 `docs/internal/` 中添加 `.gitkeep`，也不要通过例外规则重新跟踪其中的文件。
- README、`docs/README.md`、公开文档索引和公开目录树不得把 `docs/internal/` 当作可供外部访问的文档入口。
- 内部文档可以保留在开发者本地工作区，但不得提交、推送或发布到公开仓库。
- 内部文档不得存放密码、访问令牌、私钥等秘密信息；`.gitignore` 不是秘密管理工具。

`.gitignore` 只对未被 Git 跟踪的文件生效。若 `docs/internal/` 中已有文件被提交跟踪，应先检查：

```bash
git ls-files docs/internal/
```

只有在用户明确授权从 Git 索引中移除这些文件时，才执行：

```bash
git rm -r --cached docs/internal/
```

该命令会将文件从后续版本的 Git 索引中移除，但保留本地文件；它不会清除既有 Git 历史。若历史中包含敏感信息，需要另行评估历史清理和凭据轮换，不能把添加 `.gitignore` 当成历史清除。

## 三、单一事实来源与文档流转

- README 负责摘要和导航；详细定义以对应的公开文档为准。
- `docs/README.md` 是公开文档索引，只列出仓库中实际存在、可访问的公开文档。
- 正式 API、协议和接口定义应有唯一权威文档；其他页面引用它，不复制出互相独立的版本。
- 公开文档描述当前实现；开发计划、试验过程和未定稿结论保留在内部文档。
- 内部结论经过验证并决定对外承诺后，再整理为公开文档。
- 不为凑目录而创建空文档；项目规模较小时可以减少子目录。

## 四、`docs/` 公开文档目录规范

`docs/` 采用按读者任务组织的目录结构。以下是推荐起点，不要求每个项目机械创建所有目录。

```text
project/
├── README.md
├── README.zh.md
├── .gitignore
├── LICENSE
├── CHANGELOG.md
│
├── docs/
│   ├── README.md
│   ├── user-guide/
│   │   ├── installation.md
│   │   ├── configuration.md
│   │   └── usage.md
│   ├── developer-guide/
│   │   ├── architecture.md
│   │   ├── extension.md
│   │   └── development.md
│   ├── reference/
│   │   ├── api.md
│   │   ├── interfaces.md
│   │   └── compatibility.md
│   └── assets/
│       ├── images/
│       └── diagrams/
│
└── src/
```

`docs/internal/` 可以在维护者本地工作区中存在，但它必须被根目录 `.gitignore` 忽略，因此不应出现在公开仓库的实际文件树中。

### 目录职责

- `docs/README.md`：公开文档总索引，按读者任务提供入口；只列出公开且真实存在的文档。
- `docs/user-guide/`：安装、配置、日常使用、操作流程和 FAQ。
- `docs/developer-guide/`：公开架构说明、扩展开发、集成方式和贡献者开发环境。
- `docs/reference/`：API、接口、协议、数据结构、兼容性和稳定约定。
- `docs/assets/`：公开文档使用的截图、图表、示意图和其他素材。
- `docs/internal/`：仅供本地维护者使用，必须 Git 忽略，不进入公开文档索引。

文档较少时，可以直接放在 `docs/` 根目录并通过 `docs/README.md` 分类索引；当某一类文档确实增多时再建立子目录。不要为了套用目录树而创建空文件夹或空文档。

### 公开文档写作要求

- 写清文档适用对象、前置条件和适用版本（如版本差异会影响结论）。
- 以当前实现和稳定接口为依据；计划功能必须明确标记为计划。
- 详细文档可以深入解释，但不要重复 README 的完整内容。
- README 与公开文档之间使用链接衔接，避免多处维护同一份长说明。
- 补充文档写明适用语言；需要双语时使用独立文件并互相链接，不逐段中英对照。
- 公开文档中的截图、示例和命令必须与实际项目一致。
- 若公开能力存在 T1–T4、阶段、平台或功能矩阵，应清楚定义状态和适用范围；不把开发进度日志当作能力定义。
