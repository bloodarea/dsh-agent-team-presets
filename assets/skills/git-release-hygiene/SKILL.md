# Git 变更与版本交付

## 目标与边界

根据真实代码、Git 状态及项目既有约定准确组织提交与版本交付。负责版本范围、变更事实、Git 操作与风险；README、Description、Topics 的展示规范交由可用的 `github-repository-presentation`。两项 Skill 不互为必需前置条件。

## 工作方法

1. **识别真实状态**：按任务检查 `git status`、相关 diff、分支、提交、Tag、版本文件、Release 和项目现有 Git 约定。不对无关文件进行处理。
2. **沿用项目工作流**：已有提交风格、版本策略或发布流程时遵循；没有约定时提出合理建议。不强制 Conventional Commits、SemVer、PR、issue 编号或固定分支名。
3. **准确组织变更**：Commit 与 PR 反映真实修改及其目的；Changelog 与 Release Notes 基于可核对的版本范围、代码差异、合并 PR 或交付产物。优先写用户可理解的实际增量，不照搬技术日志或逐条提交。
4. **保护已有工作**：不擅自 `git add .`、删除未知未跟踪文件、覆盖用户改动、清理工作区或重写提交历史。识别敏感信息与混入的无关修改；对重置、覆盖、强制推送、Tag 改写等高风险操作先明确影响、恢复方法与授权。
5. **区分状态**：代码已修改、已检查、已提交、已推送、已构建、已公开发布分别核实，不能用其中一种状态冒充另一种。
6. **执行授权**：明确授权的普通 Commit、Push、PR 或 Release 可在规定范围直接完成，不反复请示；新的高风险或超范围动作须另行确认。仍需符合真实工具权限和平台审批。
7. **核查交付**：复核目标版本、提交范围、实际 Git/远端状态和必要的兼容、升级警示。不能执行的核验明确列出，不虚构发布成功。

## Release / Changelog / PR 文字规范

**语言形态：完整中文版 + 完整英文版，两个独立段落。**

- 先写完整中文全文，再写完整英文全文；不要把一句中文和一句英文并排、交替或逐条对照。英文不是中文的逐行注解，而是可直接独立阅读的完整对应版本。
- 结构：`## 中文` → 完整中文内容；`## English` → 完整英文内容。CHANGELOG 按版本分节后，每节内部同样先中文后英文。
- 中文段落内的类别标题用中文（`新增`、`优化`、`修复`、`重要说明`）；英文段落内用对应英文（`Added`、`Improved`、`Fixed`、`Important Notes`）。两份各自内聚，不混排。
- 只保留确有内容的类别。条目数量统计的是面向使用者的独立变更事项，不是代码行数、文件数或 Commit 数；同一事项不要重复计数。事实不足时先核实或标记待确认，不编造数字或版本日期。
- 着重说明使用者感受到的功能、优化或修复，不展开底层实现、长日志和大量 PR 明细；Breaking Change、必要迁移或已知风险不能因追求简短而隐藏，两种语言都必须写全。
- GitHub Release 标题已经显示版本时，正文不必再写重复大标题。
- README 属于 `github-repository-presentation` 的范围：那里用**独立中文文件与独立英文文件互链**做语言切换，不在同一文件里逐段双语。本 Skill 只负责 PR 描述、CHANGELOG 与 Release 正文的两种语言版本。

## 交付

简明提供实际完成的操作、提交/版本范围、真实验证结果和尚未执行或需要授权的行为；不自动创建 Changelog、Tag、Release 或额外管理文件。
