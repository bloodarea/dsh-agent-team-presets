# GitHub Release 与版本自述规范

GitHub Release 面向项目用户和关注者。采用参考 DeepSeekHarness 的**中文完整区块在前、英文完整区块在后**的结构。两种语言各自独立、完整可读；禁止逐条中英交替，也禁止在同一 Bullet 中使用 `中文 / English` 拼接。

## 一、推荐结构

```markdown
[中文](#中文) | [English](#english)

## 中文

用一段简短文字概括本次发布最值得用户关注的变化。

### 新增功能
- ...

### 体验优化
- ...

### 问题修复
- ...

### 其他变更
- ...

### 重要说明
- ...

## English

A concise summary of the most important user-facing changes in this release.

### New Features
- ...

### Improvements
- ...

### Bug Fixes
- ...

### Other Changes
- ...

### Important Notes
- ...

Full Changelog: <verified-previous-tag>...<verified-current-tag>
```

只保留有真实内容的章节，不为凑齐分类创建空标题。GitHub Release 标题已显示版本号时，正文不重复版本标题。

## 二、语言组织

- 先写完整中文区块，再写完整英文区块。
- 可在顶部提供 `[中文](#中文) | [English](#english)` 导航。
- 中文区块内使用中文，英文区块内使用英文；技术名称、命令、快捷键、API 和专有名词保留原文。
- 英文应自然、完整、可独立阅读，不要求逐字直译；技术事实、行为边界、风险和承诺必须与中文一致。
- 禁止逐条中英交替，禁止 `中文描述。 / English description.` 形式。
- 不因追求篇幅短而遗漏限制、兼容性或迁移信息。

## 三、开头摘要

- 中文区块开头用一段简短文字说明本次发布的核心价值或最值得关注的变化；英文区块提供对应摘要。
- 摘要应具体，避免“本次更新包含多项优化”等空话，也不要重复罗列后续所有 Bullet。
- 默认不添加“新增 X 项、优化 Y 项、修复 Z 项”等数量统计。只有用户明确要求或项目已有稳定惯例时才使用。
- 不将 Commit 数、文件数、代码行数当作用户变更数量。

## 四、变更分类

| 中文标题 | English heading | 内容 |
|---|---|---|
| 新增功能 | New Features | 新增的用户能力、工具、接口或工作流 |
| 体验优化 | Improvements | 已有功能的易用性、性能、稳定性或交互体验改进 |
| 问题修复 | Bug Fixes | 修复错误行为、崩溃、数据丢失或兼容性缺陷 |
| 其他变更 | Other Changes | 值得用户了解但不属于前三类的公开变化，如支持范围、依赖或文档约定调整 |
| 重要说明 | Important Notes | 破坏性变更、升级迁移、已知限制、安全提醒或必须提前了解的条件 |

分类规则：

- 没有内容的分类省略。
- 同一事项只归入最合适的一个分类，不重复描述。
- `其他变更` 不用于倾倒内部重构、纯代码清理或用户无法感知的琐碎提交。
- `重要说明` 是风险与使用提醒区，不是普通功能分类；仅在确有重要提醒时出现。
- Breaking Changes、迁移步骤和重要兼容性变化必须醒目呈现。

## 五、单条变更写作

每个 Bullet 描述一项可理解、可核验的用户可感知变化。优先采用：

**变化对象 + 具体行为变化 + 用户影响或适用边界。**

- 保留帮助用户理解功能行为的关键细节，如快捷键、参数、阈值、作用范围、兼容条件和默认行为。
- 删除无关内部实现过程、类名堆砌、文件清单、调试流水账和逐条 Commit 摘录。
- 避免“优化性能”“修复若干问题”“重构核心逻辑”等空泛描述，应说明具体改善或修复结果。
- 紧密相关的实现细节可以合并；彼此独立的用户能力不要强行合并。
- 不夸大改善程度，不写未经验证的性能数字或绝对化承诺。
- 中英文事实等价，不能让英文版遗漏中文中的限制、参数或风险。

示例：

```markdown
### 体验优化

- 画布聚焦后可使用 `V` / `M` 切换选择与框选工具；方向键移动 1px，按住 `Shift` 时移动 10px，文本编辑状态下保留原有按键行为。

### Improvements

- When the canvas is focused, use `V` / `M` to switch between selection and marquee tools. Arrow keys nudge by 1px, or 10px with `Shift`, while text editing keeps its existing keyboard behavior.
```

## 六、版本系列说明

仅在新版本系列首个 Release Candidate、正式大版本、重要里程碑，或本次发布覆盖较长变更区间时，考虑在摘要中交代版本背景。

说明应包含可核实的起始版本、比较范围和发布重点。不要每个补丁版本都机械添加。版本范围和日期必须来自真实 Tag、Release 或项目记录。

## 七、贡献者署名

- 某项用户可见变更能够明确对应贡献者时，可在该条末尾标注 GitHub 用户名，例如 `@username`。
- 贡献者身份必须由合并 PR、Commit 作者或项目明确记录确认；不得猜测或仅凭提交邮箱推断 GitHub 用户名。
- 中文、英文区块的署名保持一致；英文可使用 `by @username`。
- 无法可靠确认时省略，不强制每条 Bullet 添加署名。

## 八、Full Changelog

- 仓库地址、上一版本 Tag 和当前版本 Tag 均已确认时，在 Release 末尾提供版本比较链接。
- 格式：

```markdown
Full Changelog: https://github.com/OWNER/REPO/compare/v1.2.0...v1.3.0
```

- 比较范围必须与本次 Release 的真实变更范围一致。
- 不得猜测仓库所有者、仓库名或 Tag；信息不足时省略链接。

## 九、版本自述原则

Release 文案是面向用户的版本说明，不是开发工作汇报。优先呈现用户能获得什么、行为发生什么变化、有哪些需要注意的限制；底层实现细节只在确实影响使用、集成或升级时保留。
