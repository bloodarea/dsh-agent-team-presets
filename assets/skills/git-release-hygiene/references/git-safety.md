# Git 操作与版本安全规范

## 一、检查真实状态

根据任务范围检查：

```bash
git status --short --branch
git diff
git diff --cached
git log --oneline -n 10
git tag --sort=-version:refname
```

按需要检查分支、版本文件、远端 Release、项目脚本和既有 Git 约定。以上命令仅为检查示例，应按仓库实际情况选择，不要求无差别全部执行。

- 识别已修改、已暂存、未跟踪和冲突文件。
- 区分用户已有改动、本次任务改动和无关改动。
- 核对本次变更范围的起点与终点。
- 不根据工作区文件时间或口头猜测推断版本范围。

## 二、Commit 与版本策略

- 沿用项目既有 Commit 风格、分支策略和版本约定。
- 没有约定时先提出建议，不强制 Conventional Commits、SemVer、固定分支名或 PR 工作流。
- Commit 标题简洁说明主要目的；正文按项目惯例补充背景和细节。
- 版本号、预发布标识、Tag 和 Release 标题必须与项目策略一致。
- 撰写 Release Notes 不代表已创建 Tag 或 Release。

## 三、保护已有工作

禁止未经授权：

- `git add .` 或将无关文件一并暂存。
- 删除未知未跟踪文件、覆盖用户修改或清理工作区。
- `git reset --hard`、rebase 改写共享历史、强制推送。
- 删除或重写已有 Tag。
- 执行会覆盖远端状态的同步操作。

对高风险操作，先说明：

1. 将改变哪些本地或远端状态。
2. 可能影响哪些提交、文件、协作者或 Release。
3. 可行的备份和恢复方式。
4. 操作失败时如何停止或回滚。

取得明确授权后再执行，并遵守工具权限和平台审批要求。

## 四、交付状态必须分别核实

以下状态不可互相替代：

- **Modified**：工作区文件已修改。
- **Checked**：差异或内容已检查。
- **Committed**：Commit 已创建。
- **Pushed**：Commit 已推送到远端。
- **Built / Tested**：构建或测试实际执行并得到结果。
- **Released**：Release 已在目标平台成功公开。

不得把本地 Tag 当作远端 Release，不得把准备好的文案说成已发布，也不得把未执行的测试说成通过。

## 五、授权与执行

- 用户明确授权的普通 Commit、Push、PR 或 Release，可在授权范围内执行，不必重复请示。
- 新出现的高风险动作、超出授权范围的远端操作或可能覆盖他人工作的操作，必须重新确认。
- 无法执行的核验或操作应如实列出，不得声称成功。
