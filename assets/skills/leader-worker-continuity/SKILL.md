# Leader Worker Continuity

## 目标与范围

本 Skill 仅供队长使用，补充 `leader-long-task-orchestration` 的执行者生命周期管理。它负责任务切片、短会话接续、异常恢复和执行者替换；不重复定义需求对齐、整体计划模板或 Agent 通信协议。

- 长程任务状态需要连续。
- 单个执行会话可以结束。
- 执行者实例可以替换。
- 核心研发工作默认由执行者完成，队长负责编排、协调和验收。

## 复用现有规范

- 长程需求、产品基线、滚动规划和阶段验收：使用 `leader-long-task-orchestration`。
- 队长派发和结果回收：使用 `agent-leader-communication`。
- 执行者单个切片的实现和验证：使用 `executor-short-task-workflow`。
- 独立工作包的并行条件与边界：按需使用 `agent-subagent-orchestration`。

本 Skill 不新增 TASK 命令字段、STATUS 状态或另一套汇报格式。派发继续使用 `TASK_ID`、`TASK`、`LIMITS`、`DONE`、`REPORT`；执行者继续使用 `STATUS`、`TASK_ID`、`CHANGES`、`TESTS`、`BLOCKERS`。

## 基本运行模型

1. 队长是长生命周期的任务编排者，维护整体目标、依赖、进度和验收基线。
2. `executor` 是团队的核心执行角色，承担实际研发；该角色可以有多个并发实例，各自负责一个切片。
3. 每个执行者会话优先处理一个边界清楚的任务切片。
4. 一个逻辑任务可以跨多个执行者实例接续；接续时保留原 `TASK_ID`，只更新剩余工作范围。
5. 切片之间无依赖时，可以并发调度多个执行者实例，各自推进一个切片；切片之间存在依赖、共享文件或共享契约冲突时按依赖顺序串行。并发前确认执行路由、写入边界和宿主容量。

## 工作流程

### 1. 理解需求并建立交付物视图

在切片前，先从用户请求中提取：

- 目标用户与要解决的问题；
- 用户可见功能、主要使用流程和预期结果；
- 明确范围、排除项、约束与验收期待；
- 尚未确定的产品行为、权限、数据规则和界面选择。

产品功能、业务规则、用户流程和界面歧义交用户裁决。不要把产品决策伪装成技术任务，也不要在关键产品歧义未解决时并行实现可能相互冲突的方案。

把目标转化为可观察的交付物，例如数据能力、API、用户界面、业务流程、迁移、文档和测试。交付物清单用于推导任务，不要求每个交付物都独立成为一个切片。

### 2. 工程探查与事实收集

先检查已有文档、任务计划和已知工程事实，避免重复调查。存在两个或以上实质独立的工程事实调查方向时，必须使用 `agent-subagent-orchestration` 的 `DISCOVERY` 模式并行探查；按调查域拆分，例如架构与调用链、目标模块现状、测试体系、平台集成、文档契约。每个孙代理默认只读，提交结构化事实、来源位置、风险和未知项。

队长只把必要的探查结论带回主会话，不转发完整扫描日志。队长负责合并重复发现、解决事实冲突、复核影响架构或范围的关键事实，并将稳定事实写入项目已有权威文档或计划。执行者在获派切片中可通过 `IMPLEMENTATION` 孙代理完成独立工作包所需的局部代码探查与实现；若执行者需要多个独立的纯只读调查方向，应将调查问题和边界交回队长，由队长按 `DISCOVERY` 模式发起探查，避免扩展或改写原技能的角色分工。

单一、轻量调查由队长直接完成；不得为了使用孙代理而制造无价值拆分。孙代理创建条件、权限、任务卡和通信格式完全遵循原样复用的 `agent-subagent-orchestration` 技能。

### 3. 建立依赖关系并决定切片粒度

将交付物整理为依赖关系：哪些必须先确定，哪些可以独立实施，哪些共享接口或文件，哪些必须在集成阶段共同验证。先稳定共享契约，再分派依赖它的工作。

按以下维度决定切片边界：

1. **独立验收价值**：切片结束后是否能单独检查一个真实结果？
2. **依赖完整性**：所需接口、数据结构和前置产物是否已经明确？
3. **工作所有权**：是否能明确模块、文件或调查域的唯一负责人？
4. **上下文闭合度**：执行者能否只凭必要背景、引用路径和任务契约完成工作？
5. **风险与验证**：是否有清晰的局部测试，且失败可以局部修复或接续？
6. **交接成本**：拆分带来的独立验收和恢复收益是否高于重复理解、集成与通信成本？

优先按可独立交付的用户行为、模块能力、稳定接口或工程成果拆分，不按页面数量、文件数量、类/函数数量或固定会话轮次机械切分。强依赖工作按顺序执行；互不依赖且写入边界明确的工作才考虑并行。

### 4. 决定切片数量并形成滚动计划

切片数量由交付物、依赖、工作所有权、复杂度和验收边界推导，不设固定数量。队长应能说明每个切片为何独立，以及为何没有继续拆分或与相邻工作合并。

- 一个简单、单一目标的需求可以只有一个切片。
- 一个跨模块功能可能需要多个顺序切片。
- 多个独立调查域可由孙代理并行探查，但调查结果仍由队长统一归纳。
- 执行者收到的单个切片若包含两个或以上实质独立、可分别验收的编码工作包，按 `agent-subagent-orchestration` 的 `IMPLEMENTATION` 模式并行执行。
- 共享接口未确定、文件冲突明显或工作高度耦合时，先确定契约或按阶段串行执行。

采用滚动规划：当前切片和下一切片细化到可派发程度；更远阶段保留目标、主要依赖和待确认事项。探查结果或实际实现改变原先判断时，更新计划，不强行维持最初切片数量。

### 5. 生成切片契约

每个切片必须有一个主要结果，并明确输入、范围、依赖、权限、验收和交付证据。沿用 `agent-leader-communication` 的原有派发格式，不新增通信协议：

```text
TASK_ID: <stable task ID>
TASK: <one primary outcome>
LIMITS: <scope, permissions, constraints and relevant dependencies>
DONE: <verifiable acceptance criteria>
REPORT: <required result, changed paths and verification evidence>
```

`TASK` 与 `REPORT` 必需，其余字段按原通信技能要求使用。不要把整段主会话历史粘贴给执行者；提供最小充分背景、权威文档位置、代码入口和已确认决策。

### 6. 建立持久状态


长程任务沿用 `leader-long-task-orchestration` 的 `DELIVERY-PLAN.md`。记录整体目标、批准范围、验收清单、依赖、重要技术决定和当前轮次。不要为每个小切片创建重复的项目总计划。

### 7. 形成可执行切片

每个切片应具有：

- 一个主要结果或交付物；
- 明确的输入、必要事实和相关文件路径；
- 清楚的工作边界、权限和依赖；
- 可观察、可复核的完成条件；
- 需要执行者返回的结果与验证证据。

优先沿模块边界、可独立验收的行为或交付物拆分。存在强依赖时按顺序执行。避免把任务拆成只有机械操作、没有独立验收价值的碎片。

切片大小根据实际任务复杂度、执行者能力、可用上下文和服务预算动态调整。不得把某个固定轮次、Token 数或时间长度写成通用上限。

### 8. 派发与执行

通过既有 `agent-leader-communication` 契约派发任务。每次只传递执行所需的背景、路径、约束和验收标准；已有事实引用来源位置，不重复粘贴整份项目文档。

执行者承担技术分析、设计、实现、调试和切片内验证。队长不把核心研发实现改由自己包办，以保持本团队的角色分工。

### 9. 验收并推进

收到执行者报告后，队长检查实际变更、测试证据、边界行为和交付要求。区分执行状态与验收状态：成员报告 `DONE` 仍需队长核验；证据不足时保留为部分完成或未完成。

切片验收通过后更新 `DELIVERY-PLAN.md` 和任务板，再细化、派发下一切片。发现新依赖或原计划不成立时，先更新计划再继续。

### 10. 执行者无法继续时接续

出现 `PARTIAL`、`BLOCKED`、`FAILED`、会话无法继续、模型服务中断、上下文或额度耗尽等情况时：

1. 判断当前执行者是否仍可恢复。若原会话可继续，优先恢复原实例；只有原实例无法继续时才创建替代实例。
2. 不依赖执行者一定能提交最后一份报告。检查持久化计划、工作区文件、Git 状态与差异、提交记录、测试结果和其他可用证据。
3. 将工作区状态分为已完成且有证据、已修改但未验证、尚未完成、存在冲突或风险的部分。
4. 保留有效修改，不因执行者终止而自动回滚、覆盖或重新实现。无法判断归属或安全性时暂停并报告队长需要的人类裁决。
5. 更新原任务记录，保持原 `TASK_ID`，写明上一执行者实例、已完成部分、剩余工作、变更文件、测试结果和已知风险。
6. 若宿主支持创建新的执行者实例，使用新的唯一队友 target，将剩余工作作为接续任务派发。新执行者先检查已有成果，再继续未完成部分。
7. 新执行者完成后，队长重新核验整个切片的验收条件，不能只验收最后一段修改。

### 11. 无法接续时

宿主不支持创建新的执行者实例、成员名册或生命周期配额耗尽、模型路由不可用、工作区状态无法安全恢复时，停止自动重试。保留当前状态，说明已确认事实、阻塞原因和恢复所需的人类操作。

## 执行者实例与宿主约束

- 团队配置中的 `executor` 是角色定义；实际召唤出来的队友是具有独立名称和会话身份的实例。
- 遵守宿主的成员名册规则。若 roster 为 append-only，每个新实例使用宿主分配的全新唯一 target；不得假设已结束成员名称可以复用。
- 创建替代实例前检查现有 roster、并发限制、生命周期名额和模型路由。失败创建也可能消耗宿主名额时，不得循环重试。
- 不声称本 Skill 能自动延长服务端会话、重置供应商额度或绕过宿主限制；它只规定任务状态恢复和重新委派策略。

## 质量与成本纪律

- 执行者是核心研发产物的主要生产者；队长主要消耗用于规划、调度、上下文整理和验收。
- 切片无依赖时优先并发以缩短交付周期；并发的前提是写入边界互不重叠，避免多个执行者同时修改共享文件。切片有依赖或会触碰同一文件时按依赖顺序串行。
- 子代理只在独立工作包确实带来收益且其模型路由、文件所有权和宿主容量明确时使用。
- 不为每个切片重复加载完整项目背景；提供最小充分上下文和持久化证据位置。
- 不因会话结束就判定任务失败，也不因有代码变更就判定任务完成。
- 不要求思维链或完整工具日志；要求可复核的成果、测试和状态。
