# Worker Recovery and Replacement

## 触发条件

- 执行者明确报告 `PARTIAL`、`BLOCKED` 或 `FAILED`。
- 执行会话已结束，且宿主无法继续该实例。
- 模型服务、请求额度或执行环境导致当前实例无法继续。
- 执行者没有留下最终报告，但工作区仍有可能存在有效修改。

`DONE` 也需要队长验收；不要把任何状态字段直接等同于整体任务验收。

## 恢复步骤

1. **检查是否可恢复**：确认原成员会话是否仍可继续。可以恢复时优先恢复，避免无必要创建新成员。
2. **读取持久状态**：读取 `DELIVERY-PLAN.md`、任务板、当前切片记录及最近一次交接信息。
3. **检查工程状态**：在权限允许的范围内检查 `git status --short`、`git diff --stat`、`git diff`、相关提交、被修改文件和测试结果。非 Git 项目则检查对应工作区文件与版本记录。
4. **判断成果有效性**：识别已完成且有证据的修改、已实现但未验证的修改、尚未实现的要求、冲突和潜在回归。
5. **保护现场**：保留用户和执行者已有工作。不得因成员终止自动 reset、clean、覆盖文件或重新生成整块代码。
6. **形成交接摘要**：记录原 `TASK_ID`、上一实例、实际变更、已运行测试、未验证项、剩余工作和风险。摘要应指向路径与证据，不复制整个项目上下文。
7. **创建替代实例**：仅当原实例不可继续且宿主允许时，创建新的唯一队友 target。把原任务 ID 和交接摘要一起派发。
8. **重新验收**：替代实例完成后，队长核验整个切片的全部 `DONE` 条件，而非只检查新实例改动。

## 替代实例的接续要求

替代实例收到任务后应先检查已有工作区和交接证据，确认：

- 哪些修改已经存在；
- 哪些修改已通过验证；
- 哪些修改仍需验证或修复；
- 哪些工作尚未开始；
- 是否存在与其他成员或用户改动的冲突。

确认后只继续剩余工作。发现交接记录与真实工作区不一致时，以可复核的实际文件和 Git 状态为准，并向队长报告差异。

## 宿主名册与配额

有些宿主对成员名册采用 append-only 规则，成员 target 在团队生命周期内不可复用。遇到这种规则时：

- 新实例使用宿主允许的全新 target；
- 不尝试用原 target 重建一个不同实例；
- 创建前查看现有 roster 和生命周期名额；
- 失败创建可能占用名额时，不循环试错；
- 名额耗尽或宿主不支持新实例时，保留交接记录并请求人类处理。

本 Skill 不假定所有 DSH/Agent Team 版本都支持同一角色的无限次实例化。具体能力以当前宿主工具和运行结果为准。

## 禁止行为

- 不因会话终止而丢弃已有修改。
- 不把未知状态标记为已完成。
- 不让替代实例从头重做整个项目。
- 不让新旧执行者并发修改同一工作区文件。
- 不绕过模型路由、权限、配额或宿主生命周期限制。
- 不进行无上限的自动重试。
