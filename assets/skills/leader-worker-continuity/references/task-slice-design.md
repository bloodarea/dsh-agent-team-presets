# Task Slice Design

## 目标

把用户提出的长程研发目标转化为一组有依赖关系、可独立派发、可验证和可接续的任务切片。切片数量由真实交付物和工程结构推导，不设固定数字。

## 决策流程

### 1. 从用户目标提取交付物

识别用户要解决的问题、目标用户、主要流程、功能边界、约束和验收期待。将目标拆成可观察的交付物类别，例如：

- 产品行为与用户流程；
- 数据模型、迁移和持久化；
- API、服务或领域逻辑；
- 页面、组件和交互状态；
- 权限、文件/媒体处理和外部集成；
- 自动化测试、集成验证和文档。

这些类别只是检查视角，不代表必须一类一个切片。产品行为和界面存在关键歧义时，先交用户裁决。

### 2. 获取工程事实

先复用项目已有权威文档、代码入口和历史调查。存在两个或以上实质独立的工程事实调查方向时，队长按 `agent-subagent-orchestration` 的 `DISCOVERY` 模式并行调查。调查方向按问题域划分，不按目录或文件数量机械切分。单一调查由队长直接完成。

执行者在其切片中遇到多个独立实现工作包时，按同一技能的 `IMPLEMENTATION` 模式分派孙代理；每个工作包可在自己的范围内读取必要代码和文档，但必须遵守文件所有权及局部验收边界。

### 3. 建立依赖图

对每个交付物标记：

- 前置条件和依赖接口；
- 可并行的工作；
- 共享文件或共享状态；
- 负责实现和验收的角色；
- 局部测试与集成测试边界。

接口、数据结构或业务规则未稳定时，不把依赖它的实现同时派发。共享文件指定唯一写入者。

### 4. 决定切片数量

每个切片尽量只有一个主要结果，并能独立验收。判断维度：

1. 是否产生独立且有意义的交付结果；
2. 是否有清晰的输入、边界和依赖；
3. 是否能指定唯一主要负责人；
4. 是否有局部验证方法；
5. 是否能在会话交接时保留明确进度；
6. 拆分后的通信、重复读取和集成成本是否合理。

切片示例（仅用于说明推导方法）：一个菜谱模块可能先有项目探查，再按稳定依赖安排数据模型/API、列表搜索、详情、创建编辑和集成验收。实际项目若已有通用 API、列表组件或数据模型，应合并或删去相应切片；如果图片处理、权限或复杂工作流形成独立验收边界，则可增加切片。

### 5. 选择串行或并行

- 当前切片无并行收益时，由一个执行者实例完成。
- 多个切片之间无依赖、写入边界互不重叠时，可并发调度多个执行者实例，每个实例推进一个切片。
- 切片之间存在依赖、共享文件或共享契约冲突时，按依赖顺序串行。
- 多个独立调查方向由队长使用 `agent-subagent-orchestration` 并行探查。
- 一个切片包含两个或以上实质独立、可分别验收的编码工作包时，执行者按该技能并行实施。
- 执行者需要多个独立的纯只读调查方向时，由执行者把调查问题交回队长，队长按 `DISCOVERY` 模式创建孙代理并回收事实，再将精简结果交给执行者。
- 共享接口未确定、工作高度耦合、多个代理会写同一文件或宿主无容量时，按阶段串行。
- 孙代理不递归派生；父代理负责整合、冲突处理和验收。

### 6. 说明拆分理由

计划中简要记录：

- 为什么这些工作构成独立切片；
- 关键依赖及先后顺序；
- 哪些工作可并行，哪些必须串行；
- 为什么相邻工作没有继续拆开或合并；
- 当前计划中的假设和待用户确认项。

不要求写长篇论证，但必须让队长能解释切片数量与边界的依据。

## 切片契约检查项

派发前确认：

1. **Outcome**：本切片结束后应出现什么可观察结果？
2. **Input**：执行者需要哪些现有事实、文档、代码入口和前置成果？
3. **Scope**：允许修改哪些模块、文件或接口？哪些内容不在本次范围？
4. **Dependencies**：哪些前置切片必须先完成？哪些工作可以独立进行？
5. **Acceptance**：哪些测试、检查或人工验证可以证明完成？
6. **Handoff**：执行者需要留下哪些文件、证据和剩余工作说明？

## 复用既有派发格式

不创建新的任务命令格式。沿用 `agent-leader-communication` 的字段：

```text
TASK_ID: <stable task ID>
TASK: <one primary outcome>
LIMITS: <scope, permissions, constraints and relevant dependencies>
DONE: <verifiable acceptance criteria>
REPORT: <required result, changed paths and verification evidence>
```

`TASK` 与 `REPORT` 必需，其余按原通信技能要求使用。替换执行者继续处理同一个切片时，保留原 `TASK_ID`，并在 `TASK` / `LIMITS` 中说明已完成部分和剩余范围。

## 切片粒度调整

- 执行者能够在当前会话内完成并验证：维持当前粒度。
- 执行者多次出现部分完成，或任务涉及多个独立验收边界：继续拆分。
- 切片过小导致重复读取和交接成本明显高于实现成本：合并相关切片。
- 模型或宿主报告资源限制：按实际限制调整粒度，不把某个具体供应商限制固化为团队规则。
- 新事实改变依赖或工作边界：滚动更新尚未执行的计划，不强行维持原始切片数量。
