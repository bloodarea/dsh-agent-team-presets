# 复杂 Bug 诊断与根因定位

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、目的与责任归属

本工作流主要供后端架构师处理需要专业诊断或架构级修复的后端缺陷。

Executor 仍负责常规前后端开发和普通局部 Bug 修复，遵循其既有 `executor-short-task-workflow`。不要把所有小问题都升级给架构师。

出现以下情况时，考虑升级到本工作流：

- 故障跨越多个模块；
- 问题间歇发生且难以复现；
- 涉及事务或数据完整性；
- 涉及并发、竞态、死锁；
- 涉及安全边界或权限绕过；
- 涉及资源生命周期；
- 出现明显性能回归；
- 正常的一线排查和合理修复仍无法解决。

后端架构师可以直接修改后端生产代码和测试，修复已经确认的根因。这不意味着架构师承担所有常规后端编码。

## 二、不可妥协的原则

在调查根因之前，不要先修补表面症状。

看似合理的解释不等于证据。测试通过只有在它覆盖真实故障路径、能够识别目标缺陷时才有价值。

## 三、阶段一：建立快速反馈循环

优先投入精力建立一个快速、可重复的通过/失败信号，覆盖真实故障路径并断言准确症状。

根据实际情况优先考虑：

1. 在正确边界编写失败的单元、集成或端到端测试；
2. 在开发环境中使用可重复的 HTTP/curl 脚本；
3. 使用带有测试数据和预期输出的 CLI 调用；
4. 重放已捕获的请求、事件或调用轨迹；
5. 建立调用真实代码路径的最小测试程序；
6. 对输入敏感或间歇性故障使用属性测试、模糊测试或压力循环；
7. 使用版本/配置二分法或新旧版本差异测试。

反馈信号必须满足：

- **准确：** 断言用户报告的真实症状，而不只是进程没有崩溃；
- **相关：** 确实经过受影响的代码路径；
- **可重复：** 结果稳定；间歇性问题应有足够高的复现概率；
- **足够快速：** 能够反复运行；
- **可由 Agent 执行：** 尽可能不依赖未记录的人工步骤。

通过减少无关初始化、固定可控的时间和随机性、隔离状态、收窄断言等方式缩短反馈周期。

如果无法建立可信的反馈循环，应暂停直接修复，不要把猜测当成根因。说明已经尝试的方式，并请求缺少的环境、脱敏日志/调用轨迹/HAR/core dump、测试数据，或安全诊断授权。

只有生产日志、调用轨迹等间接证据时，可以继续收集证据和排序可证伪假设，但必须把相关结论标为待验证，并明确无法复现带来的限制；不得据此声称根因或修复已经得到完整验证。

## 四、阶段二：复现并最小化故障

1. 运行反馈循环，确认能够复现报告中的症状。
2. 捕获准确错误、错误输出、状态损坏、请求顺序或性能数据。
3. 重复运行，确认复现稳定性。
4. 每次只减少一个输入、调用方、数据、配置或操作步骤，然后重新运行。
5. 保留所有能够让故障发生的必要条件。

不要根据一个相似但不同的故障继续推理。存在正确测试边界时，应将最小复现转化为回归测试。

## 五、阶段三：提出可证伪假设

对于足够复杂的问题，在探测之前列出三到五个按可能性排序的假设。

每个假设必须说明：

- 怀疑的原因；
- 支持该原因的证据；
- 如果假设成立，应该观察到什么现象；
- 能够确认或推翻它的最小探测。

假设必须能够被证伪。不要罗列泛泛的可能性，也不要过早认定第一个看起来合理的原因。

如果队长掌握的上下文或决策可能显著改变处理优先级，应同步当前假设；但不要因此阻塞安全且必要的调查。

## 六、阶段四：有针对性地采集证据

每次探测都应能区分特定假设。一次只改变一个变量。

优先使用：

1. Debugger、Profiler 或 REPL 检查；
2. 模块和接口边界上的定向日志；
3. 受控故障注入或最小轨迹重放。

避免无差别记录所有信息，再从大量噪声中寻找线索。

临时诊断日志必须遵守：

- 使用唯一标记，例如 `[BUGFIX-<task-id>]`；
- 脱敏密钥、凭据、Token、个人信息和敏感载荷；
- 只记录证明假设所需的字段；
- 完成前移除临时诊断代码，除非已明确批准保留为正式可观测性能力。

跨模块故障应沿相关边界追踪数据和状态：输入、校验、服务/模块、持久化、事件/队列和输出。找出不变量第一次被破坏的位置。

性能问题应先测量基线，再修改代码。根据问题使用计时程序、Profiler、查询计划、资源指标或负载画像。日志数量不能代替性能测量。
