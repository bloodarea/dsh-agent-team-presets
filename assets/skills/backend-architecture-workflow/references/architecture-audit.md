# 架构审计

> 本文是主 Skill 的按需参考资料。仅在接受架构审计、模块边界梳理、依赖治理或"为什么改不动"类调查时读取。

## 一、先取证，再下结论

在画图或评价之前，先确认能看到什么。用户已给出目录树或相关文件内容时可直接进入第二步；否则按下面顺序主动取证：

1. **顶层结构**：只列前两层目录，识别模块边界。不要一上来递归全仓。
2. **入口与清单**：读包清单或主配置（`package.json`、`go.mod`、`pom.xml`、`Cargo.toml`、`pyproject.toml`），确认语言、框架与已声明依赖。
3. **依赖边**：按语言各跑一次 import/require 检索，用来发现跨模块引用。限制在有限匹配条数内，避免把上下文塞满。
4. **大模块**：任何顶层目录文件数超过 10 时，读它的 `index.*`、`main.*` 或 `__init__.*`，弄清它自述的职责。

能回答下面三件事就可以停止取证：顶层模块有哪些、谁 import 谁、扇入或扇出最高的是哪个。

模块规模超过约 100 个顶层文件或嵌套超过 4 层时，在报告里注明哪些区域是**实际读取**的、哪些是**推断**的。

## 二、先画出模块依赖图

在评价任何风险之前先画图，图是后续结论的共同底座。规则：

1. **节点**用顶层目录或可部署单元，不用单个文件。
2. **分组**：每个架构分层或顶层目录一个 `subgraph`（如 UI、Domain、Infrastructure）。
3. **边**：实线箭头从依赖方指向被依赖方；存在循环依赖时用带标签的虚线（`-.->|cyclic|`）。没有循环就只有实线。
4. **节点上限**约 50 个；低风险叶子模块合并进父节点。
5. **高扇出**（> 5）的节点在标签里注明：`HighFanOut["ModuleName (fan-out: 7)"]`。
6. **配色最后加**：风险扫描完成后再写 `classDef` 与 `class`，按 P1/P2/P3 对应红/黄/绿。没有任何发现时全部标绿。
7. **方向**默认自上而下；架构明显是左到右流水线时才用 `graph LR`。

单仓多服务时，把每个可部署服务或库当作顶层模块，画服务之间的依赖，而不是它们内部的包。

## 三、按四个维度扫描

**依赖方向（最优先）**
循环依赖；箭头向上流动（高层领域依赖低层基础设施）；被广泛依赖的稳定模块 import 了频繁变动的模块；扇出 > 5；"什么依赖什么"没有一致答案。

**领域表达**
模块名是否贴合业务词汇；是否有一个 `services` 层装走全部业务逻辑而领域对象只是数据结构；是否有模块越界（计费逻辑长在用户模块里）；外部系统接入处是否有防腐层。

**变更传播**
哪些模块是"爆炸半径热点"（改它就要改很多别处）；依赖图能否解释某些功能为什么开发缓慢。

**偶然复杂**
是否有整层架构不产生价值；是否有模块的职责无法用一句话说清；是否有为了假想需求预建的抽象。

## 四、接缝密度评估

接缝（seam）是"不修改源码就能替换行为"的位置，通常是接口、配置点或依赖注入边界。接缝密度是**可测试性与可演化性**的代理指标。

- **基础设施边界没有接缝**：能否在不修改被测模块的前提下，把真实数据库、文件系统或 HTTP 客户端换成测试替身？不能，就意味着架构强迫用集成测试去覆盖本该用单元测试的场景。
- **接缝塌陷**：原本可隔离测试的模块，接缝被移除（依赖注入点被直接构造替代，或全局单例替换了注入的协作者）。
- **遗留区域缺接缝**：没有明显注入点或接口边界，任何改动都要穿透整个调用栈才能替换行为。

全部模块在基础设施边界都有清晰接缝时 → 无发现。缺失或塌陷时报 P2，并在修复里指明具体模块与需要恢复/引入的注入点。

## 五、Conway 检查（可选）

架构与团队结构是否互为镜像？只在用户提供了真实的团队/所有权信息时才做，未知就注明"缺少上下文"并跳过。

- P1：模块归属与职责严重错配，每次改动都要跨团队同步（例：计费模块归 A 队但内含 B 队负责的鉴权逻辑）。
- P2：两队分别维护做着同样事情的目录，理论上有摩擦但尚未真的造成发布协调成本。
- 不算发现：单队维护一个多逻辑模块的单仓——Conway 错配要有**彼此独立的团队**才有意义。

## 六、交付

报告顺序：**依赖图 → 各维度的发现 → 接缝与 Conway 结论 → 优先级建议**。

每条发现给出模块名、图上的对应节点、症状、后果、最小修复方向与严重程度。图中节点名必须与本文章节里的发现对应得上——图是证据，不是装饰。

只读审计不修改代码。需要落地修复时，把最小修复方案作为建议交给队长，由队长按文件所有权派给对应角色。
