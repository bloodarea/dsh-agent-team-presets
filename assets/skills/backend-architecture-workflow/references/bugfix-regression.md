# 根因修复、回归验证与收尾

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、修复根因并增加回归覆盖

1. 选择能够覆盖真实故障模式的测试边界。
2. 存在正确测试边界时，先将最小复现转化为失败的回归测试，再实施修复。
3. 确认测试确实因为报告的原因失败。
4. 实施能够解决已验证根因的最小改动。
5. 运行回归测试并确认通过。
6. 再次运行原始、未缩减的反馈循环。
7. 运行受影响模块和契约的相关回归测试。

如果不存在正确的测试边界，应记录限制。无法覆盖真实调用链的浅层测试会制造虚假的信心。将缺失的测试边界作为架构/可测试性问题记录，并在扩大修复范围前咨询队长。

特殊问题的验证要求：

### 数据、事务和迁移

- 使用隔离测试数据和非生产环境；
- 保留既有不变量和向后兼容；
- 规划迁移和回滚行为；
- 未获明确授权，不得执行破坏性的生产 SQL 或数据修复。

### 并发问题

- 覆盖相关的交错执行、取消、关闭、重试或锁生命周期；
- 需要压力或重复测试时，不得用一次成功运行作为结论。

### 安全问题

- 同时验证攻击路径和预期权限边界；
- 不得对授权范围之外的系统实施攻击性复现；
- 避免暴露密钥和敏感数据。

## 二、清理并关闭问题

宣布完成前：

- 重新运行原始反馈循环；
- 确认回归测试通过；没有正确测试边界时明确说明原因；
- 移除临时诊断日志和标记；
- 删除临时测试程序，或明确标注保留的诊断夹具；
- 检查最终 diff，移除无关变更；
- 报告已确认根因，以及证据如何证明修复针对该根因。

如果多次合理修复都失败，应停止叠加补丁，重新检查架构、数据流和原始假设，并与队长协商。连续失败意味着应该重新质疑设计，不能成为继续堆叠临时绕过方案的理由。

## 三、完成报告

报告至少包含：

- 准确症状和复现命令/测试；
- 根因及其证据；
- 已验证和已排除的假设（必要时）；
- 修改文件与行为；
- 回归测试和相关测试的实际结果；
- 适用时的性能基线和修复结果；
- 临时诊断产物清理情况；
- 剩余风险、证据缺口和待决策事项。

不能仅因为修改后的代码看起来合理，就声称 Bug 已经修复。
