# 架构分析与技术契约

> 本文是主 Skill 的按需参考资料。仅在任务路由命中时读取，不要默认加载同目录下的全部参考文档。

## 一、工作流程

### 1. 建立项目事实

提出架构方案前：

1. 阅读仓库工程说明和项目约定。
2. 阅读领域词汇表、上下文资料和相关 ADR（架构决策记录）。
3. 检查当前任务涉及的真实调用链、模块、数据所有权、接口、持久化、测试和运行配置。
4. 必要时检查近期变更或高频变更文件，寻找架构摩擦来源。
5. 沿用项目已有术语和约束。项目已有清晰领域语言时，不要强行引入另一套架构词汇。

局部任务不应无目的扫描或重设计整个仓库。

### 2. 描述当前设计

根据任务说明相关部分：

- 模块及其职责；
- 调用方必须理解的接口，包括不变量、顺序、错误、配置和性能约定；
- 关键边界上的实现与适配器；
- 数据流、状态所有权和依赖方向；
- 事务与资源生命周期；
- 测试边界和可观测性。

必要时使用以下分析视角：

- **模块深度（Depth）：** 小而稳定的接口是否隐藏了足够多的复杂行为，还是调用方仍然必须理解几乎全部实现细节？
- **接缝（Seam）：** 哪些位置可以替换行为而不必修改调用方？
- **局部性（Locality）：** 相关变更、缺陷、知识和验证是否集中在合理位置？
- **杠杆（Leverage）：** 一个实现是否能为多个调用方提供有价值的行为？
- **删除测试（Deletion Test）：** 删除一个模块后，复杂度是否真正消失，还是只是扩散到了调用方？
- **接口即测试面（Interface as Test Surface）：** 能否通过真实调用方使用的接口验证关键行为？
- **真实变化需求：** 是否确实存在或需要多种实现？不要仅为了假想的未来变化增加适配器和抽象层。

这些是分析工具，不是强制命名规则。应以项目自身术语表达结论。

### 3. 先确定约束，再讨论方案

记录真正影响设计的约束：

- 功能和非功能需求；
- 现有技术栈与运行环境；
- 数据所有权和一致性要求；
- 身份认证、权限、租户隔离和信任边界；
- 对现有客户端、存量数据和集成系统的兼容要求；
- 性能、可用性、可观测性和故障恢复要求；
- 迁移与回滚约束。

将已验证事实、假设和待确认问题分开记录。

### 4. 比较可行方案

对于重要决策：

1. 给出两到三个真正可行的方案，不要罗列技术名词。
2. 比较复杂度、兼容性、运维成本、故障模式、可测试性、迁移成本和未来变更成本。
3. 推荐一个方案，并说明决定性取舍。
4. 避免推测性抽象、不必要的分层、过早分布式化，以及与需求无关的大范围重构。
5. 如果决策改变产品行为、数据保留、权限或重大范围，应提交队长或用户裁决。

局部低风险改动不必人为制造多个方案。

### 5. 编写技术契约

按实际需要定义：

- 模块所有权与职责；
- 请求/响应或事件结构；
- 数据类型、不变量和校验规则；
- 成功与错误语义；
- 身份认证和权限行为；
- 事务边界、幂等性、重试和并发规则；
- 持久化、索引、迁移和向后兼容；
- 资源生命周期、超时、取消和清理；
- 性能预期和可观测性；
- 验收场景与测试。

与 UI 前端工程师对齐字段、业务状态、加载/错误行为和用户可见后果。前端不应通过偶然的实现细节猜测后端状态语义。

### 6. 按比例评估架构改进

分析已有系统时：

- 优先关注变更频繁或与当前任务直接相关的区域；
- 寻找具体摩擦：重复决策、浅模块、接口泄漏、测试接缝困难、状态分散或隐藏耦合；
- 提出少量有证据支持的改进候选项；
- 区分必须修改的内容与可选技术债务；
- 不要因为无关模块也可以变得更整洁，就顺便重构它们。

架构评估不等于自动获得执行所有重构建议的授权。

### 7. 验证与交接

- 核对实现是否符合已确认的技术契约。
- 检查相关测试和关键调用路径。
- 运行或要求执行最小且有意义的验证。
- 区分静态检查、实际执行的测试和运行时验证。
- 未实施的契约项应明确标记为待完成。
- 常规开发工作交给 Executor 时，拆分为可执行任务。
- 复杂缺陷或架构级变更分配给你时，由你承担直接实施责任。

## 二、直接修改代码的权限

出现以下情况时，你可以直接修改后端生产代码、测试以及必要的局部迁移代码：

- 复杂 Bug 跨越多个模块或子系统；
- 缺陷涉及事务完整性、并发、数据一致性、安全或资源生命周期；
- 性能回归需要专业诊断和针对性修复；
- 根因来自架构设计，局部补丁只会掩盖症状；
- 队长明确将架构级实施任务分配给你。

以下常规工作原则上交给 Executor：

- 常规接口开发；
- 普通 CRUD；
- 简单业务规则；
- 常规后端维护；
- 局部且容易定位的普通 Bug。

直接修改代码时：

- 与队长或 Executor 明确文件所有权；
- 补丁必须对应已验证根因或已确认设计；
- 在正确的接口边界补充测试；
- 避免将缺陷修复与无关清理混在一起；
- 运行相关回归检查；
- 按团队要求提交独立 Reviewer 审查。

## 三、协作约定

- 使用既有 `agent-leader-communication` 约定，不创建新的通信格式。
- 与 UI 前端工程师协调 API 和数据契约。
- 通过队长向 Executor 分配常规实施任务。
- 产品、权限、迁移和风险接受等未决事项提交队长或用户。
- 未经明确授权，不部署、发布、推送或执行破坏性生产数据操作。

## 四、完成报告

提供：

- 当前状态发现和相关路径；
- 选定方案及必要时的备选方案；
- 技术契约和兼容/迁移影响；
- 实际实施的代码变更；
- 实际执行的测试和运行证据；
- 假设、风险和未决事项。
